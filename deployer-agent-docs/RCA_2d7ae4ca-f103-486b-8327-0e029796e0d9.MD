# RCA — Standalone Android APK shows SIMULATED vehicle data (jarvis-ai-1486)

## Verdict
The **current committed source is correct** and the **latest published OTA already contains the fix**. The problem is NOT stale JS in the published OTA and NOT a missing build-time env var. The problem is that **the user's installed native APK is running an OLD, pre-fix JS bundle, and the corrected OTA update is not reaching that binary.** The remediation is to **REGENERATE the native build** (not merely re-publish an OTA).

## Decisive evidence — the installed binary is running stale JS
- Current source `frontend/src/vehicle/simulationProvider.ts` hardcodes the demo identity as **2018 Jeep Wrangler JL, VIN `1C4HJXEG9JW174532`**.
- The user's installed app shows **"2016 Jeep Compass"** (+ demo DTC P0300).
- These do not match ⇒ the device is running a **JS bundle OLDER than the current source** — a demonstrable preview↔device mismatch. This is forensic proof, independent of runtimeVersion reasoning.
- Corollary: with the CURRENT `createProvider()` logic, native builds can NEVER reach `SimulationProvider` when `EXPO_PUBLIC_VEHICLE_MODE=ble` — in **either** dev or production (`__DEV__` only gates the sim escape hatch, and only when mode is `sim`/`simulation`). So the mere fact that the device shows simulation proves it is NOT running the current bundle, regardless of `__DEV__`.

## Why the OTA is not reaching the installed APK (root cause candidates, all point to "regenerate native build")
1. **`expo-updates` is not in the committed source.** It is installed + configured only inside the ephemeral OTA build workspace. Any native binary that was built WITHOUT the expo-updates native module compiled in has **no update client at all** and can NEVER pull an OTA — it is permanently pinned to its embedded bundle. This is the most likely blocker.
2. **runtimeVersion is injected at build time, not committed.** The OTA is pinned to RV `1.0.0` (appVersion policy). If the installed APK's embedded runtimeVersion ≠ `1.0.0`, or it points at a different EAS project, or its channel isn't mapped to branch `production`, the update is ineligible and silently ignored.
3. **No native build run exists in this deployment's history.** `list_versions` shows only two runs — `initial` (Aug 9) and `redeploy` (Aug 13), both backend+OTA pipeline runs. There is **no `android_build`/`ios_build` run**. The deploy pipeline only publishes OTA Updates + the backend image; it does not produce the APK. So the installed APK was produced outside the recorded run history (an earlier/external native build) from stale JS.

## Answers to the 5 questions
1. **Which bundle is prod vs installed running?** Latest published OTA (group `3f87c73b`, branch production, RV 1.0.0) = CURRENT source, includes the `service.tsx` guard and the sim production throw. The **installed APK = stale pre-fix JS** (proven by "2016 Jeep Compass" ≠ current source's "2018 Jeep Wrangler JL"). Prod OTA is NOT stale; the device just isn't receiving it.
2. **EXPO_PUBLIC_VEHICLE_MODE embedded at build time?** For the published OTA: **`ble`** (confirmed exported into Metro bundle; `.env` + all `eas.json` profiles = ble). For the user's installed APK: not readable from here, and irrelevant — that old bundle predates the mode-based native guard.
3. **`__DEV__` in the installed build?** Not readable from the binary. Logically moot: current JS never yields Simulation on native with mode=ble in EITHER dev or prod, so simulation on-device ⇒ old JS. `eas.json build.<profile>.env` is read by **EAS Build (native builds)**; the deployer's `eas update` lane reads `frontend/.env`. Both say `ble`.
4. **Does installed runtimeVersion match latest OTA?** Latest OTA RV=`1.0.0` (appVersion, remote source). Installed RV not verifiable here. Given (a) `expo-updates` absent from source and (b) unverified RV/channel/project match, **do not assume an OTA re-publish alone will reach the device.** Regenerate the native build.
5. **Is `react-native-ble-plx` compiled into the installed binary?** In SOURCE yes (dep 3.5.1 + plugin + permissions) → a fresh native build WILL include it. Whether the *installed* APK has it can't be inspected. Note: missing ble-plx would cause `UNAVAILABLE`, not simulation — so it is NOT the cause of this symptom; it only matters for BLE working after the stale-JS issue is fixed.

## Remediation (precise)
1. **PRIMARY — Regenerate the native Android build (and iOS) from current source** via the Publish to Play/App Store (native build) flow, then have the user **uninstall the old APK and install the freshly generated binary.** This bakes in the corrected JS + ble-plx + a working expo-updates client. This is the only reliable fix.
2. **Do NOT rely on re-publishing an OTA alone** — the Aug-13 OTA already contains the fix and has not reached the device; old binaries may lack the updates client entirely, and RV/channel match is unverified.
3. **Source hardening so this can't recur (recommended for E1 to apply before the rebuild):**
   - Add `expo-updates` to `frontend/package.json` dependencies so the native binary always ships with a working update client.
   - Commit `updates.url` (project `4f7e910e-accf-4adc-bcd1-76665f149612`), an explicit `runtimeVersion` (or policy), and the EAS `projectId`/`extra.eas` into `app.json`, rather than relying on ephemeral injection at publish time. This keeps installed binaries and published OTAs on the same runtimeVersion/channel so future OTAs actually land.
4. **Not a build-time env problem** — `EXPO_PUBLIC_VEHICLE_MODE=ble` is correctly present in `.env` + `eas.json` and confirmed embedded in the published OTA. No change needed there.

## Class
Config/architecture + preview↔device mismatch. Not a manifest fault (no manifest change applies). Not reproducible in the eph sandbox (no node/npm/yarn; and the fault is native-binary/OTA-delivery state, not runnable app code). Diagnosed from build logs + source, not reproduced.
